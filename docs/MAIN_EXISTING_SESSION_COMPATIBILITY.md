# Existing mode session validation: main compatibility map

This is a source comparison, not a migration, a database test, or a hosted API claim. The current checkout is `00230540ee2f0a81a0b7dc11c07701cbe9343b9c`; the historical Wave 3 checkout inspected is `885d8b6fc5a9712c4aa4ce69817a1867c10b6240`. Exact source paths appear below. Neither branch state nor a historical local test result proves that the proposed function works against current main.

## Existing authority and proposed addition

Current [0030_mode_flow_sessions.sql](../supabase/migrations/0030_mode_flow_sessions.sql) creates immutable `public.mode_flow_sessions` and `public.mode_flow_requests`. A session pins `token_hash`, tenant, flow, installation, version, service, mode, profile, renderer/parent origins, target/policy revisions, installation-history sequence, and a 15-minute `[issued_at, expires_at)` window. The session has composite foreign keys to the installation, bound version and installation history. Its insert trigger compares the current installation and latest history before accepting a row. Current `lumin.mode_session_authority(t uuid,f uuid,iid uuid,r text,parent text)` locks active tenant and flow, selects an enabled installation and deployment profile, checks renderer origin and hosted/iframe parent-origin policy, and returns that installation. The function is a source of current authority for both issue and submit; the caller's IDs are selectors, never authority.

Current `public.mode_issue_flow_session(uuid,text,text,text,text,uuid,bigint,bigint) returns jsonb` accepts installation ID, token hash, renderer and parent origins, profile version, expected version, target revision and policy revision. It checks those inputs, uses `mode_session_authority`, checks current version/target and policy, inserts one pinned session or handles a same-hash repeat, rejects expired repeats, and returns a bounded issue receipt with `schemaVersion`, session/installation/mode/profile/origin/version/revisions/issued/expires/render fields. Current `public.mode_submit_flow_request(text,text,text,text,jsonb,jsonb,timestamptz) returns jsonb` looks up a token hash, rechecks current installation authority, pinned session identity and expiry, and performs request/booking writes with server-side validation. These are separate issue and submit paths; the proposed validation must never invoke issue as a read fallback or create/rotate a session.

The historical `supabase/migrations/0031_mode_session_validation.sql` at `885d8b6` adds exactly one `security definer` function, `public.mode_validate_existing_flow_session(text,uuid,uuid,text,text,text,uuid,bigint,bigint,timestamptz,timestamptz) returns jsonb`. Its arguments are token hash, session ID, installation ID, renderer origin, parent origin, profile version, expected version ID, expected target revision, expected policy revision, issued timestamp and expiry timestamp. It calls `lumin.mode_session_protocol()` and validates hash, IDs, profile spelling, safe revisions, finite timestamps and the exact 15-minute relationship. Malformed non-origin input raises `MODE_SESSION_INVALID` / SQLSTATE `22023`; malformed origin raises `MODE_SESSION_INVALID_ORIGIN` / `22023`. Missing or no-longer-authorized session raises `MODE_SESSION_FORBIDDEN` / `42501`.

The historical read first discovers the session by hash, session ID and installation ID without treating discovery as authority. It then calls current `mode_session_authority` for the discovered tenant/flow and supplied origins, checks profile and policy revision, reloads the session against that tenant/flow, verifies a bound version and service ID, locks the active service, then locks and compares the session's pinned version, service, target/policy revisions, mode, profile, origins and issued/expiry timestamps. It rejects expiry before and after building the same bounded issue-receipt shape through `mode_session_render`. The session lookup remains tenant/flow-bound. Current [0029_mode_installations.sql](../supabase/migrations/0029_mode_installations.sql) separates `apply` (new current version and incremented target revision) from `policy` (enabled/origins and incremented policy revision), with immutable history rows. The local mode-installation repository calls `mode_apply_flow_version` and `mode_update_flow_policy` for those paths. The validation source does **not** compare `issued_history_sequence` with the latest history or require the installation's current version/target to equal the old pin on this read; these semantics need an explicit product/security decision for rotation. It does not read a separate session-revocation column: disabling the installation, changing policy/origin authority, deactivating tenant/flow/service or expiring the session are the visible denial routes. A newly required per-session revocation rule would need separate design and proof.

The historical function explicitly revokes `EXECUTE` from `public`, `anon`, `authenticated` and `service_role`, then grants it only to `service_role`. Current 0030 does the same for issue, submit and owner history. The proposed service-only grant must survive migration and privilege inspection; no customer or owner browser token may call the function directly. Its response is a bounded JSON object with the existing issue receipt fields, not a new bearer secret. Its error labels are not permission to expose SQL details in HTTP.

## Current composition and dependencies

Current [apps/api/src/main.ts](../apps/api/src/main.ts) composes `createFlowHttpServer`, `createFlowRepository` and Supabase identity verification into the hostable API. [apps/api/src/http.ts](../apps/api/src/http.ts) still has the earlier customer `/api/installations/:id/sessions` issue and `/api/flow-sessions/request` submission routes. [apps/api/src/repository.ts](../apps/api/src/repository.ts) uses the earlier `issue_flow_session`/`submit_flow_request` RPC signatures. The newer mode-session repository and contracts under `apps/api/src/mode-session-*` are described in source as local/disposable; `mode-session-repository.ts` invokes the 0030 `mode_issue_flow_session` and `mode_submit_flow_request` SQL but does not call the proposed historical validation RPC. The historical `packages/action-api/server/mode-session-validation.ts` at `885d8b6` contains an internal `validateExisting` transport and outcome classification; it is not wired into current `apps/api/src/main.ts`. A future hostable read must use trusted server context and current auth/tenant admission, strict bounds and safe error mapping. Copying the historical transport or SQL into the current host is not proven by this map.

Dependencies that must be checked on the main schema before any additive migration: `public.mode_flow_sessions`, `public.mode_flow_installations`, `public.mode_flow_installation_history`, `public.bound_flow_versions`, `public.services`, `public.tenants`, `public.flows`, `lumin.installation_profiles`, `lumin.mode_session_protocol`, `lumin.mode_session_time`, `lumin.mode_origin`, `lumin.mode_session_authority`, `lumin.mode_session_render`, `lumin.mode_session_limit` and `lumin.mode_session_stamp`. Keep the accepted [0031_overbooking_backstop.sql](../supabase/migrations/0031_overbooking_backstop.sql) intact. The historical `0031_mode_session_validation.sql` has a number collision with that accepted migration, and the historical `0033_text_field_prompts.sql` has been reported to collide with PR79's proposed `0033` at an earlier review point. Refresh current PR/migration claims before assigning any new additive number; this document does not assert current PR79 state.

## Disposable verification before adoption

Run against fresh, disposable databases in **both supported extension layouts**, applying current main migrations first and the reviewed, renumbered semantic delta afterward. Each transaction must satisfy `lumin.mode_session_protocol()` in both layouts: read-committed isolation and bounded nonzero statement, lock and idle-in-transaction timeouts. Do not apply a historical 0031 file by filename or touch live data. Capture schema diff, `pg_get_functiondef`, exact `pg_proc` signature, owner/search path, grants, function dependencies and migration rollback/reapply evidence. Test SQLSTATE and redacted application outcomes rather than raw SQL text.

| Case | Evidence required |
| --- | --- |
| Authorized existing hosted and iframe sessions | Exact pinned receipt, renderer/parent policy, no new session/request/booking row, same-hash read remains a read. |
| Missing or forged hash/session/installation; cross-tenant or cross-flow source | `42501` and no data; discover/reload/lock sequence remains tenant-bound. |
| Invalid input, origin, revision, timestamp or receipt binding | `22023` for malformed parameters; otherwise deny without leaking which source row failed. |
| Disabled installation, changed policy/origins, inactive tenant/flow/service, missing bound version | Deny; preserve old pin semantics deliberately if installation version/target rotated without revocation. |
| Expiry before call, while waiting on source/session locks, and during render | Deny at the final clock check; no issuance or writes. |
| Concurrent installation rotation, disable, origin/policy change and read | Controlled lock ordering; read either returns an authorized consistent receipt or denies. Prove no stale grant after the changing transaction commits. Per-session revocation is a separate, unimplemented design question. |
| Grants and rollback | Only service role executes; anon/authenticated/public denied. Fault injection and transaction rollback leave accepted 0030 and 0031 behavior unchanged. |
| Both extension layouts | Run the same tests and compare qualified function resolution and grants; no search-path-dependent behavior. |

Unverified here: a live database's actual extension layout, current PR79 head, deployed migration history, hosted mode-session read wiring, and production credentials/TLS. This source comparison did not execute SQL; the separate disposable compatibility harness records later local test evidence. New provider credentials, live migrations, activation and deployment remain release decisions after exact-candidate CI, independent review, Runtime Guardian and Release Governor evidence.
