# Worker roster foundation

0021 provides seven tenant-scoped tables: roster state, workers, access, crews, members, service eligibility and explicit UTC shifts. No jobs, assignments, allocation, worker API, execution, provider or tenant-role grant is implemented.

Only service_role may execute the public roster_provision and six typed roster mutation functions. The actor UUID is a trusted verifier output, never a client assertion; every call rechecks active tenant/current BUSINESS_OWNER through flow_actor. Missing ownership or roster state fails closed. Provision is idempotent and returns the current version. Mutation functions require expected roster version and return its next value; failed entity/constraint checks roll the version change back. Put functions require explicit p_create; create-existing/update-missing conflicts. Identity rows are retained/deactivated; no worker/access/crew/shift delete RPC exists. crew_member_set removes a relationship under the fence. service eligibility is deactivated, not deleted.

Lock order: tenant/current owner SHARE locks, roster CAS UPDATE lock, then child rows. Every supported roster write must go through these narrow RPCs, and allocation must hold roster SHARE before reading children through commit. No raw table permissions exist for anon/authenticated/service_role, including TRUNCATE/REFERENCES/TRIGGER; private helper execution is revoked. This hard privilege boundary does not claim arbitrary superuser DML is serialized. Fixtures use the same mutation RPCs. Whole-tenant deletion cascades are a separate lifecycle operation and conflict with the active-tenant SHARE lock. Service deletion is blocked by eligibility FK NO ACTION: existing service writers cannot cascade an unfenced eligibility mutation. Worker/crew cascades originate only from new, non-writable identity tables or whole-tenant teardown. Auth-user deletion is blocked while access rows reference it.

Worker access binds one immutable tenant/user/worker tuple and permits at most one active login per worker. Grant mutation increments permission_version, including reactivation; safe-integer limits fail without wrap/reset. Worker and crew active flags do not confer login authority. Shifts retain their worker identity and use active=false for retirement; finite start/end UTC values are authoritative, source_time_zone must exist in PostgreSQL's timezone registry. No local-time/DST conversion is implied.

Mandatory dependency before any future job reads: replace access mutators AND worker deactivation to atomically revoke/increment affected assignments; this foundation cannot revoke nonexistent assignment tables and offers no assignment read surface. Crew changes must never dynamically expose old jobs to new members. Allocation/policy fences and capacity/quantity claims are separate migrations.

Validation: worker_roster_tests.sql runs in a rolled-back transaction with explicit synthetic records and checks authority, CAS rollback, immutable/foreign bindings, single active bridge, access revocation, versions, labels, shifts, service deletion boundary, forced RLS and privileges. worker_roster_concurrency.py requires WORKER_ROSTER_TEST_DISPOSABLE=1, loopback PGHOST and lumin_ PGDATABASE; observes actual PgSleep/transactionid contention, requires one committed CAS winner, and cleans exact random fixtures with bounded process timeouts. Superuser fixture setup is local only; no production seeding or credentials are supplied.
